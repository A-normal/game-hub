# 模块与插件开发约定

本文定义 Game-Hub 的配置式模块开发契约。模块通过 `config/modules.json` 装配；可使用 `GAMEHUB_CONFIG` 指定另一份文件。功能进展与验证边界放在插件文档和过程记录中。

## 包组织与边界

四个分类是 packages/core、packages/channel、packages/provider、packages/plugin。core 是通用核心包，其它三类下每个具体实现都是二级独立包，拥有自己的 package.json、公开入口、测试和配置 schema。

- channel：原生事件与标准事件之间的适配、平台鉴权、文本交付、连接生命周期。
- provider：社区和外部服务的协议、认证、凭据、签名、设备和网络错误。一个 provider 可以服务多个 plugin。
- plugin：游戏或其它业务，依赖注入的能力完成命令和数据处理。chatAi 属于 plugin，不是 core 的特殊分支。
- core：注册、依赖解析、装配、事件、配置、路由、权限、身份与通用存储、生命周期；不得内置具体游戏的默认配置或业务 SQL。

跨包只使用公开接口；禁止读取旧宿主安装目录或另一个插件内部路径。不得使用旧宿主全局 Bot、redis、segment、NoteUser。新增合规模块不应要求编辑 core 或 app.mjs 的专用 import 列表。

## 标识与依赖

模块统一声明稳定 id、kind、contractVersion、公开入口、配置 schema 和所需能力。id 和 kind 不随展示名称或命名空间变更。

- pluginId 不等于 gameId。游戏属性是业务领域元数据，不是所有插件的必填字段。
- plugin 可不依赖 provider，也可按能力依赖多个 provider；不能强制声明一个 community。
- 凭据、激活角色和客户端在路由需要时才解析。普通工具、帮助和 AI 路由不应提前触发游戏角色查询。
- provider 的能力需明确输入、输出、认证方式、区服、错误、取消和幂等语义；不以一个无类型 request(any) 替代全部契约。
- 插件专属数据由插件存储接口及版本化迁移维护；共享身份、权限和任务设施由 core 提供。业务表不能无限堆入核心 Vault。

## 配置装配

装配配置声明模块、启用状态、依赖绑定和参数。发现到的模块只有在配置显式启用后才能初始化。仅登记本地受信的模块入口，不允许用户通过聊天命令注入任意 import 路径。

装配层负责校验配置、契约版本、重复 id、能力依赖、命名空间冲突，并给出定位到模块的错误。模块导入应无启动副作用。包布局变更须同步 workspace glob、依赖名称、启动器、测试、lockfile 和容器构建复制路径。

## 命令声明

每条路由使用稳定 routeId、纯语义词元、参数 schema、权限、所需能力和处理器。前缀和别名属于命名空间配置。

“角色名 + 面板”等动态参数通过有边界的路由契约实现，不能枚举有限旧角色后宣称任意角色可用，也不能注册无界正则抢占其它插件。

快捷指令配置映射到 pluginId + routeId + 参数，与正常路由共享校验和权限。保留原始事件供诊断，不把正文改写后重新穿透整条分发链。

处理器的 `ctx.args` 是按空白分词的便捷参数；`ctx.argumentText` 保留命令后原始参数文本（去除外围空白）。接收 JSON 等结构化文本时使用后者，避免破坏字符串内部连续空格或换行；快捷指令将固定参数置于原始尾部之前。插件仍须自行限定输入大小、校验字段、保护私密输入，不能把原文写入日志。

## 动态命令文案

core 提供统一命令格式化能力：

```js
const bindCommand = ctx.commands.format({ pluginId: 'zzz', routeId: 'loginQr' });
await ctx.event.reply(`请先发送「${bindCommand}」绑定账号。`);
```

格式化必须：

1. 以稳定模块与路由标识查找当前有效配置，验证目标模块启用及路由可用。
2. 在调用时解析前缀、别名和必要的命令参数，选出无歧义且实际可调用的形式。
3. 前缀与别名等价且独立：每个标记后直接接词元，`%帮助` = `zzz帮助` = `绝帮助`；提示优先渲染主前缀。共享前缀会把该指令路由到其它插件时，选择本插件可用的独立别名；不能生成误导调用。禁止把前缀与别名拼接成 `%zzz帮助`。
4. 对空前缀、只有别名、多个插件共享前缀和不可用路由定义明确行为；不回退到固定 #、*、%。
5. 覆盖帮助、错误、未绑定提示、参数说明、成功后的下一步指引和定时消息。
6. 在异步流程和定时任务发送提示时重新解析，不能把启动时或任务建立时的前缀永久缓存。
7. 避免提示继续推介未启用模块或已经移除的图片路由。

其它解释性文字可正常作为文案维护；凡其中包含可执行命令，都走同一格式化能力。命名空间变更不等于自动保留旧命令，兼容入口必须由配置显式声明。

## 路由阶段与 chatAi

路由阶段按如下顺序执行，所有插件遵守同一契约：

```text
显式命令 → 业务声明的普通文本入口 → 已配置启用的兜底插件
```

命令匹配成功后，先检查权限和已装配能力，再调用处理器。结果区分：

| 结果 | 含义 | 可否进入兜底 |
| --- | --- | --- |
| NOT_MATCHED | 当前路由未认领此事件 | 仅当整个事件属于普通文本且尚未消费时允许 |
| HANDLED | 已消费事件，无论是否需要回复 | 不允许 |
| FAILED | 路由执行失败或能力不可用 | 不允许 |
| DENIED | 权限拒绝 | 不允许 |

明确使用命令入口但没有匹配的输入，按未知命令处理，不发送给 AI。回复交付失败不能被当成“未处理”而重复调用其它插件。

chatAi 可以声明显式命令以及普通聊天兜底，但不得抢占业务命令或重复回复。它不要求 gameId、community 或游戏角色；通过独立模型 provider 能力请求服务。模型接口切换、作用域、限额和敏感信息边界沿用通用配置与权限契约。本轮只定义这些边界，不实现插件、不调用模型。

## 数据、权限与错误

- 使用标准事件的 unifiedUserId、platform、sender.id；原始平台用户标识不从正文解析。当前事件没有 originalId 契约。
- 网络调用有界超时和重试；HTTP、业务返回码、凭据失效、未解锁、无数据和服务失败分别处理。
- 签名与实际 query/body 一致，区服、设备及凭据类型显式区分。
- 数据按适用的用户、账号、游戏、区服、群和周期隔离；多人共享社区账号也应分别选择主角色。
- 缓存保存来源、更新时间及规则版本；刷新失败不能先删除有效历史。
- 多表绑定使用事务；不得从孤立凭据猜测账号归属。
- Cookie、token、authkey、ticket 与密钥不进入普通日志、群回复或导出。
- 管理配置与全局操作校验权限；非幂等外部操作不能因超时盲目重放。

## 文本与业务任务

数据处理与文本格式化分开测试。报告包含主体、周期、数据时间和关键状态；缺失字段显示缺失，不填默认满级、满星或示例属性。长列表提供筛选或分页，遵守渠道长度限制。

不实现业务图片路由、图片资源管理、截图渲染或视觉能力，也不在帮助中保留此类空入口；认证必需的扫码二维码不属于业务图片功能。

抽卡自动更新是核心链路：命令 → 获取有效授权 → 有界分页 → 校验、去重、持久化 → 查询和分析。JSON 导入仅作迁移／补录辅助。面板优化按业务需求保持官方全角色、公开展柜和指定角色更新的语义，不引入旧宿主兼容层。

自动签到、提醒等任务默认关闭，显式开启后持久化。任务由统一应用生命周期管理，定义重试、离线交付、重启恢复与日期／周期去重；不创建额外后台进程。定时通知中的命令在实际发送时动态格式化。

## 验收与来源

至少验证：模块发现和配置启停、依赖与路由冲突、热变更命名空间后的各类提示、命令／普通文本／兜底边界、权限与数据隔离、持久化、取消和关键竞态。禁止只检查标题就判断功能完成。真实在线验收与模拟测试分别记录。

本地自有项目中的定制需求是内部演进依据，不列入外部致谢。实际移植的第三方代码仍须保留来源与许可；只允许许可明确且宽松兼容的实现，AGPL 只核对功能。

模块的功能清单、验证状态和变更过程放在具体插件文档或专门记录；根 README 说明平台目标、结构、配置方式和开发约定。
