# 绝区零扫码登录修复

本次仅修复独立 Game-Hub 的扫码登录。上游功能补齐未实施，需另行确认。未引入旧插件代码、云崽依赖或旧数据库，也未修改部署配置。

## 根因

容器在 2026-10-25 14:59:27 已记录米哈游扫码授权成功，随后在 `IdentityVault.bindUser` 抛出 `Cannot read properties of undefined (reading 'toString')`。扫码处理读取了事件里不存在的 `originalId`；网关提供的发送者 ID 实际为 `sender.id`，平台字段为 `platform`。

另有后续缺陷：扫码写入裸 Cookie 字符串，而读取时只尝试 JSON 解析，导致后续查询使用空凭据；独立写入凭据、绑定和角色还会在中途失败时留下部分数据。

## 当前行为

- 使用当前事件的 `unifiedUserId`、`platform`、`sender.id` 保存绑定，不硬编码 QQ 平台。
- 保留此前实际完成过扫码授权的默认 app 模式；显式附加 `web` 或“网页”使用 web 模式。未因绑定错误而切换工作中的默认授权协议。
- 保存独立的 stoken、ltoken 和 Cookie token；保留值中的 `=`，支持 v2 Cookie 和多个 Set-Cookie；不会用 stoken 冒充 ltoken。
- 角色查询成功且返回合法列表后，才原子保存凭据、聊天身份、绑定、角色与主角色。最高等级角色被选为主角色；合法的空角色列表会明确说明未创建绝区零角色。
- 接口拒绝凭据、角色列表异常或写入失败时，不报告成功，不留下部分绑定；重试失败会恢复此前的凭据与主角色。
- 单个 HTTP 请求最多等待 15 秒，整个登录流程最多 3 分钟。轮询可容忍少量网络抖动；取消、重新发起或超时会结束当前会话，晚到的旧响应不能写入或清理新会话。
- 二维码消息未送达时不继续轮询。不把上游凭据响应、ticket 或含 stoken 的 URL 写进扫码日志。
- 新 Cookie 使用已有客户端支持的 `{ "ck": "..." }` JSON 格式；旧裸字符串只在读取时适配，不批量改写数据库。存储仍使用现有 Vault 机制，本改动不声称新增加密功能。

## 使用与验收

下文以 `%` 为例，实际请使用总线配置的插件前缀。

1. 更新服务代码后，在私聊发送 `%扫码`，使用米游社 App 扫描二维码并确认授权。
2. 应收到“米游社账号扫码绑定成功”及实际角色信息；有多个角色时默认选择最高等级角色。
3. 发送 `%角色列表`，确认绑定属于当前聊天用户。后续查询会从该绑定读取 Cookie。
4. 需要取消时发送 `%扫码终止`；需要重新扫码时直接发送 `%扫码`，旧会话自动失效。
5. 如需网页模式，发送 `%扫码 web`。

修复不会依据失败时残留的凭据猜测其聊天账号归属。更新后重新扫码即可通过正常授权流程更新凭据并补全绑定；无需删除身份库。

运行本地自动化验证：

```powershell
node tests/zzz-qr-login.test.mjs
npm test
```

扫码测试使用真实事件整形器、调度器、SQLite Vault 和 provider，模拟米哈游响应；覆盖身份字段、凭据读回、事务回滚、取消和替换竞态等。它们验证本地登录链路，不代表已通过真实手机扫码或官方接口实测。此次没有启动或重启容器，现有运行实例仍使用更新前代码；容器部署和真实手机扫码验收尚待执行。

## 变更与回滚边界

代码变更限于扫码处理、身份库的 Cookie 读写和原子保存能力、测试入口与新增测试。没有新增依赖、表结构迁移或生产数据修改。回滚时只还原本次补丁，保留本轮前已有的未提交修改；无需删库或清理已有绑定。
