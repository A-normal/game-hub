# Game-Hub

Game-Hub 是一个通过配置组合 **channel、provider 和 plugin** 的可扩展应用仓库。core 提供统一契约和运行基础；新增游戏、社区或业务能力，以增加独立包并声明配置的方式接入，不要求修改 core 中的游戏列表。

绝区零是一个业务插件，米游社是一个 provider，NapCat 是一个 channel。它们不是仓库能力的上限。聊天 AI 同样作为独立 plugin 接入，不要求游戏身份或米游社账号。

## 设计目标

- **配置装配**：配置决定启用哪些模块、实例参数、路由命名空间及权限；模块目录的存在不等于自动启用。
- **持续扩展**：允许增加任意数量符合契约的 channel、provider 和 plugin，避免为每个新游戏修改启动入口或核心分支。
- **模块独立**：业务插件不依赖特定渠道，不导入另一个插件的内部文件；provider 不承担消息路由和展示职责。
- **纯文本数据流**：数据获取、业务处理与文本展示分离。不实现面板图片、原图、换装图片、图片攻略、截图渲染或图片识别。扫码登录二维码属于身份认证载体，保留其必要支持。
- **真实数据**：失败、未解锁、无记录和未支持有不同结果；不得用固定示例数据填充真实报告。
- **运行可控**：模块声明生命周期，任务可启停；自动签到和提醒必须显式开启，不在模块导入时产生网络请求、监听或计时任务。

## 四类模块与目录约定

目录按以下职责组织；新增包应同步处理 workspace、包入口、测试及容器构建。

```text
packages/
  core/                    核心包：契约、注册、路由、配置、身份、存储与生命周期
  channel/
    napcat/                NapCat / OneBot v11 适配包
    <channel-id>/          其它渠道适配包
  provider/
    mihoyo/                米游社协议、认证和游戏数据服务
    <provider-id>/         其它社区或外部服务
  plugin/
    zzz/                   绝区零业务插件
    chat-ai/               独立 AI 插件（P1.1：交互式模型向导、双管理员、健康检查、上下文与回复）
    <plugin-id>/           其它游戏或业务插件
config/                    模块装配及运行配置
docs/                      公开的模块契约、插件文档与部署说明
tests/                     跨模块契约与集成测试
```

每个具体模块都有自己的包边界和 package.json。目录按职责分类，包通过稳定名称引用，禁止将磁盘相对路径当作跨包接口。

| 模块 | 职责 |
| --- | --- |
| core | 通用事件和结果契约、模块注册与依赖解析、配置、命名空间、权限、身份和存储服务、任务生命周期 |
| channel | 平台鉴权、原生事件转换、文本收发与真实交付结果 |
| provider | 社区或外部服务协议、凭据、设备、签名、网络请求和结构化错误 |
| plugin | 业务命令、数据加工、业务规则和文本结果；可以是游戏插件，也可以是 chatAi 等通用插件 |

依赖方向是各模块依赖 core 的公开契约；运行时由装配层注入需要的能力。plugin 可声明零个或多个 provider 及能力要求，不强制拥有 gameId、单一 community 或激活游戏角色。provider 也可服务于多个游戏插件。

## 模块接入与配置约定

新增模块的流程：

1. 在相应分类下增加独立包，声明稳定 id、类型、契约版本、配置 schema、所需能力和公开入口。
2. 实现并测试模块公开契约，不在导入阶段执行启动副作用。
3. 在装配配置中登记模块和实例参数，显式设置启用状态；凭据使用独立配置或环境注入。
4. 装配层验证依赖、能力、配置和路由冲突，再按生命周期初始化；错误应指出具体模块。
5. 在模块自己的文档中说明命令、数据来源、权限与验收范围。README 不维护某个游戏的功能完成率。

模块统一导出 `configSchema` 和 `createModule({config, dispatcher, vault})`。装配文件为 [config/modules.json](config/modules.json)，也可通过 `GAMEHUB_CONFIG` 指定；`enabled: false` 的模块不会被导入。参数中的 `{ "$env": "变量名", "required": true }` 从环境读取；数值环境变量使用 `"as": "number"`。快捷入口以 `text + routeId + args` 配置，直接调用同一条路由。

发现与装配必须是通用机制。不得在 core 中加入“如果游戏是 zzz”之类的业务分支，也不得依靠手工追加 app.mjs import 才能接入每个新插件。磁盘中新增但未启用的模块不执行初始化。

## 路由与命名空间约定

- pluginId 是稳定的内部标识；前缀、展示名、命令别名和快捷入口是可变配置。gameId 只在确有游戏语义的数据和能力中使用。
- 路由声明稳定 routeId 和语义词元，不包含部署前缀，不注册无边界的全局正则。
- **所有提示中的命令都必须由 core 的统一命令格式化服务在发送时生成**，包括帮助、未绑定提示、错误、操作示例和定时通知。不能缓存一个前缀后长期使用，也不能偷偷回退到固定的 #、* 或 %。
- 命令格式化必须使用目标插件在当前上下文的有效命名空间，产生该路由实际可接受且无歧义的调用形式。
- 提示应给出最短可用形态：前缀与别名是**等价且独立**的调用标记，`%帮助` = `zzz帮助` = `绝帮助`；提示只渲染主前缀，不把前缀和别名拼接成 `%zzz帮助`。
- 命名空间改变后，新提示立即使用新配置；旧入口只有作为显式兼容别名配置后才继续有效。
- 快捷指令是配置映射，接受同样的冲突、权限和参数验证，不通过修改原始消息再交给其它插件抢答。

具体标准见 [插件开发约定](docs/plugin-development.md)。

### 指令帮助

所有插件与系统管理统一使用“帮助”“帮助 <指令>”“帮助 全部 [页码]”。常用清单只展示简短用途，完整参数与作用范围按需查询。重复兼容叫法已收敛；使用时加上插件当前命名空间，详见 [指令说明与迁移表](docs/commands.md)。

## chatAi 的扩展边界

chatAi 是独立聊天插件，包含上下文、人物卡文件导入、服务与多模型配置、双管理员权限，以及可选事件响应、表情素材、主动问候、显式记忆与手动摘要，详见 [chatAi 插件说明](docs/chat-ai.md)。其路由阶段与扩展边界保持以下规则：

1. 先处理已注册的显式命令。
2. 再处理业务插件声明的普通文本入口。
3. 最后才执行用户配置启用的兜底插件。
4. 已消费、已回复、执行失败或权限拒绝的事件不进入 AI；明确属于命令但无法匹配的输入按未知命令处理。
5. AI 插件不强制要求游戏角色；模型访问属于独立 provider 能力，其配置、费用控制和权限不得进入 core 的游戏分支。

## 业务插件约定

游戏功能和定制行为放在对应插件中。以 ZZZ 为例：

- 抽卡的核心链路是“更新抽卡命令 → 授权与分页同步 → 持久化 → 抽卡记录／分析命令”。JSON 导入用于历史迁移或补录，不代替自动更新。
- 面板按来源和调用者权限刷新，明确官方全角色与公开展柜的不同能力；指定角色更新、缓存和冷却由插件负责。
- 社区认证和协议由 provider 提供，插件不自行维护另一套签名与凭据实现。
- 评分、伤害、统计等先形成可验证的数据，再输出文本；规则、输入、覆盖范围与数据时间可追溯。

## 开发与验证

需要支持 node:sqlite 的 Node.js；工具链和包管理器版本以仓库配置为准。

```powershell
corepack enable
corepack pnpm install --frozen-lockfile
npm test
```

测试应覆盖模块契约、配置装配、命名空间变更、冲突、权限、数据隔离、持久化、错误与生命周期。测试进程内临时资源必须关闭，不依赖常驻服务。

公开功能与接口说明放入 docs/ 或具体插件文档；实施计划、现场报告和开发过程记录放入不发布的 .private/development/。分类规则见 [文档索引](docs/README.md)。模拟验证与真实渠道／官方接口验收分开记录。

## 部署与运行约定

配置与凭据与源码分离；部署应校验模块配置、持久化路径和渠道鉴权。Compose 是一种部署方式，不参与业务契约。服务启动、升级、备份和回滚见 [部署操作说明](docs/operations.md)。

不得将 Cookie、token、authkey、登录 ticket 或密钥写入普通日志、群回复、榜单和导出文件。存储方案是否提供静态加密必须以实现为准，不能仅在帮助文案中宣称。
